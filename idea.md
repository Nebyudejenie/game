# BENGO — PRODUCTION REAL-MONEY BINGO PLATFORM
## Master Engineering, Product, Architecture & Operations Prompt

You are the **principal architect, senior backend engineer, frontend engineer, DevOps/SRE engineer, security engineer, QA engineer, database engineer, payments engineer, and product engineer** responsible for building a complete production-grade real-money bingo platform called **Bengo**.

The attached screenshot is the **visual/product reference** for the initial experience. Use it as inspiration for the game interface, but do NOT merely reproduce the screenshot. Build the complete underlying platform, business logic, security model, accounting system, multiplayer engine, administration system, and production infrastructure.

The final system must be capable of supporting **10,000+ concurrently connected players in the same live bingo game**, with deterministic game state, authoritative server-side number generation, correct prize calculation, financial integrity, and no double payouts.

---

# 1. PRODUCT VISION

Build Bengo as a professional real-money online bingo platform.

The core experience should be:

1. User opens Bengo.
2. User registers.
3. User verifies phone number.
4. User completes required age/KYC checks.
5. User deposits funds using supported legal payment methods.
6. User enters a legally permitted bingo room.
7. User selects a stake/ticket.
8. User joins the live game.
9. The server starts the game according to the configured schedule.
10. Numbers are generated by an auditable server-side RNG.
11. Every connected player receives the same authoritative game events.
12. Players mark their cards automatically/manually.
13. The system continuously evaluates winning conditions.
14. Winners are determined server-side.
15. Prize pools and payouts are calculated according to the configured rules.
16. Winning balances are credited atomically.
17. Every financial and game event is permanently auditable.
18. Players can view their tickets, game history, deposits, withdrawals, wins, losses, and statements.

The platform must feel like a **serious commercial gaming product**, not a demo.

# 6. WALLET + FINANCIAL LEDGER

This is one of the most important parts.

DO NOT implement money as a simple mutable:

```text
balance = balance + amount
```

Use an **immutable double-entry ledger**.

Every financial operation must create ledger entries.

Example:

```text
Player wallet
      |
      +---- Debit: 20 ETB
      |
Game escrow
      |
      +---- Prize allocation
      |
Winner wallet
      |
      +---- Credit: prize
```

Implement:

- deposits
- withdrawals
- stakes
- refunds
- winnings
- bonuses
- fees
- adjustments
- chargebacks
- reversals

Every transaction must have:

```text
transaction_id
reference_id
player_id
type
amount
currency
direction
status
idempotency_key
created_at
completed_at
metadata
```

Never delete financial transactions.

Never modify historical financial records.

Use compensating transactions for corrections.

Support:

```text
PENDING
PROCESSING
COMPLETED
FAILED
REVERSED
CANCELLED
```

All monetary values must use integer minor units, not floating-point numbers.

For example:

```text
20.00 ETB
```

should internally be represented safely according to the configured currency precision.

```text

# 16. ATOMIC SETTLEMENT

Settlement must be atomic.

When a winner is confirmed:

```text
validate winner
     ↓
lock game
     ↓
lock settlement
     ↓
calculate payout
     ↓
create ledger entries
     ↓
credit winner
     ↓
mark settlement complete
```

Use:

- database transactions
- unique constraints
- idempotency keys
- distributed locks where required

A winner must never receive the same payout twice.

## Prompt 3 — Game engine

> Implement `services/engine/`. This owns room state and is the only writer for a room.
>
> Build:
> 1. **Ownership.** Claim rooms with `SET room:lock:{id} {worker_id} NX EX 15`, refresh 
>    every 5 s, release on shutdown. A worker that loses its lock must immediately stop 
>    touching that room.
> 2. **Room loop** implementing the state machine in spec §3.3: IDLE → LOBBY → RUNNING → 
>    SETTLING → IDLE. One asyncio task per room; 50 rooms per worker.
> 3. **Join/leave**, staking through the ledger from Prompt 1, with the card-uniqueness 
>    constraint enforced by the database primary key on `(round_id, card_no)` — not by 
>    an application-level check.
> 4. **Calling**: walk `draw_order` every `call_interval_ms`, increment `call_index`, 
>    publish to `room:{id}`. Use a monotonic clock and correct for drift so calls do not 
>    slowly desynchronize over a long round.
> 5. **Claim validation** per spec §3.4, including the atomic winner compare-and-set, the 
>    50 ms tie window with an even split, and the false-claim lockout.
> 6. **Settlement**: one ledger transaction moving `pot_escrow` → winner(s) + 
>    `house_revenue`. Derash = pot × (10000 − house_cut_bps) / 10000, rounded **down** to 
>    2 decimals, with the remainder going to the house so the transaction still sums to 
>    zero.

>    is free, and **void them with a full refund**. Losing a round is acceptable; losing 
>    money is not.

>   ledger balanced to the cent.
> - Two simultaneous valid claims → both recorded, derash split 280/280, sums to 560.
> - A claim on a card the user does not hold → rejected, logged, no state change.
> - Round with no winner after 75 calls → every player refunded exactly their stake, 
>   house gets nothing.
> - Kill the worker mid-round, restart → round voided, all 35 players made whole.

## How to run this well

1. **One prompt per session.** Long sessions degrade; a fresh session with the spec 
   re-attached produces better code than turn 60 of a marathon.
2. **Demand tests before accepting.** If a prompt comes back without the tests it 
   specified, send it back. Untested money code is a liability, not an asset.
3. **Review Prompts 1, 3, 7, and 8 line by line yourself.** Those four are where money 
   can be lost. The rest can be reviewed at a higher level.
4. **Keep a `DECISIONS.md`** in the repo. Every time the implementer deviates from the 
   spec, record what and why. Six weeks in you will not remember.
5. **Do not skip Prompt 10.** A bingo game that stutters during the call is worse than 
   no bingo game — and you only find that out under load.

This is a real-money gambling product. Two things must be settled first, because both

The Telegram Mini App is the game. The bot is just the door. This spec defines every

## 1. Visual language

Dark, high-contrast, arcade-adjacent. The screenshot reference is close to right; here 
is the token system to formalize it.

| Token | Hex | Use |
|---|---|---|
| `--bg` | `#0B0E14` | App background |
| `--surface` | `#151A24` | Cards, panels, stat tiles |
| `--surface-2` | `#1E2532` | Unmarked number cells |
| `--text` | `#F2F5FA` | Primary text |

Restraint. Three moments only:
1. **New call** — the number badge scales 0.8 → 1.0 with a soft glow, 240 ms.

3. **Win** — the winning line pulses gold three times, then the derash counts up.

Everything else is instant. Respect `prefers-reduced-motion`: replace all three with 
plain color changes.

## 3. Interaction rules that matter

1. **Optimistic marking, authoritative correction.** A tap fills instantly; if the server 
   disagrees on reconnect, `state_sync` silently corrects. Never make the player wait 
   for a round trip to see their own tap.
2. **Countdown is server-anchored.** Client computes `seconds_left` from 
   `server_time - local_offset`, refreshed on every message. Never trust the device clock.
3. **Connection banner.** On disconnect, show a thin amber bar: "Reconnecting…". On 
   restore, remove silently. Do not throw a modal — the player is mid-round.
4. **Haptics** via `Telegram.WebApp.HapticFeedback`: light on mark, medium on new call, 
   success on win. Big feel, no cost.
5. **Back button.** Wire `Telegram.WebApp.BackButton` to navigate within the app, not to 
   close it, while a round is live. Confirm before abandoning a staked card.
6. **Offline:** if the socket is dead >10 s, freeze the board with the amber bar. Do not 
   let the client fake calls forward.
7. **No sound by default.** Add a speaker toggle; many people play in public.

# Jo Bingo — Full System Design

Real-money multiplayer bingo on Telegram. Target: **10,000+ concurrent players**, 
**200+ simultaneous game rooms**, sub-300ms number-call fan-out, zero balance drift.

This document is the source of truth. An engineer (human or AI) should be able to build 
the entire platform from this file plus the companion files in this folder.

---

## 0. Product summary

Players open a Telegram bot, register with their phone number, deposit money, then play 
timed bingo rounds against other players. Each room has a fixed stake. Everyone who joins 
a round pays the stake into a pot. The house takes a commission; the rest — the **derash** — 
goes to whoever calls BINGO first on a valid pattern.

**The core loop, 60–90 seconds:**

```
Pick a room (stake) → Pick a card (1–100) → Lobby countdown → 
Numbers called every 4s → First valid BINGO wins the derash → Next round
```

**Reference economics** (matching the screenshot the client provided):
- 35 players × 20 ETB stake = 700 ETB pot
- House cut 20% = 140 ETB
- Derash (prize) = **560 ETB**

---

## 1. Non-negotiable principles

These constrain every decision below. Violating any one of them creates either a 
cheating vector or a money-loss bug.

1. **The server is authoritative.** The client never decides what number was called, 
   whether a card won, or what a balance is. The Mini App is a renderer.
2. **Money moves only through double-entry ledger writes inside a database transaction.** 
   There is no `UPDATE users SET balance = balance + x` anywhere in the codebase.
3. **Every money-moving operation is idempotent**, keyed by a caller-supplied 
   `idempotency_key`. Retries and duplicate webhooks must be safe.
4. **The draw sequence for a round is fixed and committed before the round starts**, 
   and its hash is published to players (provably fair). No number is ever chosen 
   after seeing who holds what card.
5. **Card assignments freeze at round start.** No joining mid-round, no swapping.
6. **Realtime is a broadcast tree, not N queries.** One room tick produces one message 
   fan-out, not one database read per player.
7. **A player's session can die at any moment.** Reconnection must restore full state 
   from the server in one message.

### 2.2 Why this split

| Service | Scales on | Stateful? | Why separate |
|---|---|---|---|
| Bot | Telegram update rate | No | Telegram webhook bursts shouldn't touch game latency |
| Gateway | WebSocket connections | Connection-local only | Where the 10k sockets live; must be cheap to add replicas |
| Game Engine | Number of rooms | Yes — owns room state | Single writer per room removes all race conditions |
| Wallet | Transaction rate | No | Money code must be small, auditable, separately deployable |
| Payment | Provider webhook rate | No | Provider outages must not degrade gameplay |

### 2.3 The one rule that makes 10k concurrent work

**Exactly one Game Engine process owns any given room at any time.** Room ownership is 
claimed with a Redis lock (`SET room:lock:{room_id} {worker_id} NX EX 15`, refreshed 
every 5s). That single owner is the only writer of room state, so the entire game loop 
runs lock-free in memory. The engine publishes state deltas to `Redis PUB room:{id}`; 
every Gateway replica subscribes and fans out to whichever sockets it happens to hold.

Cost per number call: **1 Redis publish + 1 serialized JSON blob**, regardless of whether 
the room has 3 players or 3,000. This is the difference between a system that dies at 
500 users and one that idles at 10,000.

### 2.4 Capacity model

Sizing target — plan for 5× the stated goal so a viral weekend doesn't take you down:

| Metric | Target |
|---|---|
| Concurrent WebSocket connections | 50,000 |
| Connections per Gateway replica | 8,000 (so ~7 replicas) |
| Concurrent active rooms | 400 |
| Rooms per Engine shard | 50 (so 8 shards) |
| Number calls/sec across platform | 400 rooms ÷ 4s = 100/s |
| Outbound messages/sec peak | 50,000 (fan-out, batched) |
| DB writes/sec at peak | ~600 (joins + settlements, batched) |
| p99 call-to-render latency | < 300 ms |

Gateway replicas are stateless — put them behind a load balancer with sticky-by-nothing 
routing. Any replica can serve any player. A player reconnecting to a different replica 
receives a full `state_sync` and continues.

## 3. Game rules (exact specification)

### 3.1 The card

Standard 75-ball bingo. 5×5 grid, columns labelled B I N G O.

| Column | Number range |
|---|---|
| B | 1–15 |
| I | 16–30 |
| N | 31–45 |
| G | 46–60 |
| O | 61–75 |

- 5 distinct numbers per column, sorted ascending top to bottom.
- Centre cell (row 2, col 2) is a **FREE** space, always counted as marked.

**Card pool:** 100 fixed cards, numbered 1–100. Card #37 is the same grid forever. 
This is what Ethiopian players expect — they have "lucky" card numbers. Generate the 
pool deterministically from a constant seed at build time and store it in the DB as a 
`cards` table so it can never drift between deployments.

Each card number can be held by **only one player per round**. This caps a room at 
100 players. For bigger rooms, run multiple parallel rooms at the same stake rather 
than increasing the pool — 100 is part of the product feel.

### 3.2 Winning patterns

A card wins when any of these is fully marked:

| Pattern | Description |
|---|---|
| Row | any of 5 horizontal lines |
| Column | any of 5 vertical lines |
| Diagonal | either of 2 corner-to-corner lines |
| Four corners | the 4 outer corner cells |

The FREE centre counts as marked for rows, columns, and diagonals that cross it. 
Make the pattern set **configurable per room** (`rooms.win_patterns` as a JSON array) 
so you can later launch "blackout" or "postage stamp" rooms without a code change.

### 3.3 Round state machine

```
   ┌──────────┐  first player joins   ┌──────────┐
   │  IDLE    │──────────────────────►│  LOBBY   │
   └──────────┘                       └────┬─────┘
        ▲                                  │ countdown hits 0
        │                                  │ AND players >= MIN_PLAYERS
        │                                  ▼
        │                            ┌──────────┐
        │                            │ RUNNING  │◄─┐ call number
        │                            └────┬─────┘  │ every CALL_INTERVAL
        │                                 │        └─
        │      no players                 │ valid BINGO claim
        │                                 │ OR 75 numbers exhausted
        │                                 ▼
        │  after RESULT_SECONDS      ┌──────────┐
        └────────────────────────────│ SETTLING │
                                     └──────────┘
```

**Timings (all configurable per room):**

| Phase | Default | Notes |
|---|---|---|
| LOBBY countdown | 30 s | Resets to 30 only on the first join, never extends |
| MIN_PLAYERS | 2 | If not met at 0, refund all and return to IDLE |
| CALL_INTERVAL | 4 s | The heartbeat of the game |
| Max calls | 75 | Exhaustion = no winner = full refund |
| SETTLING display | 10 s | Winner animation, then next round auto-starts |

**Refund rule:** if a round ends with no winner (numbers exhausted, or lobby failed to 
fill), every entry fee is returned in full — no house cut. Encode this as ledger 
reversals, not as a new "refund" balance bump.

### 3.4 Claiming BINGO

Two modes, player-selectable via the **AUTO** toggle:

- **Manual:** the player must tap the BINGO button. Marking is manual too — they tap 
  cells. This is the "real bingo" feel.
- **AUTO:** the server marks their card and auto-submits a claim the instant a pattern 
  completes. Safer for the player, and it's what most people leave on.

**Claim validation, server-side, in this order:**

1. Round is `RUNNING`.
2. Claimant actually holds that card in this round.
3. Recompute marked grid from `called_numbers[0:call_index]` — **not** from anything 
   the client sent.
4. At least one configured pattern is complete.
5. Atomically compare-and-set `round.winner_id` from `NULL`. First writer wins.

**Ties:** if two AUTO claims complete on the same call, both are valid. Resolve by 
`claim_received_at` monotonic timestamp on the engine. If within 50 ms, **split the 
derash evenly** — do not pick arbitrarily, players notice and it destroys trust. 
Record all co-winners in `round_winners`.

**False claims:** a manual claim that fails validation costs the player nothing 
financially but locks their BINGO button for **the rest of that round**. This stops 
spam-tapping. Log it; three false claims in a session triggers a soft rate-limit.

### 3.5 Provably fair draw

Players who lose money need to believe the draw wasn't rigged against them. This 
matters more in a small market where reputation travels by word of mouth.

**Before the round opens (LOBBY start):**
1. Engine generates `server_seed` = 32 random bytes.
2. Publishes `server_seed_hash` = SHA-256(server_seed) to all clients and stores it.

**At round start (RUNNING):**
3. `client_seed` = concatenation of the sorted card numbers actually in play + round id. 
   Players collectively influence it; nobody controls it.
4. `draw = Fisher-Yates shuffle of [1..75]` seeded by 
   `HMAC-SHA256(server_seed, client_seed)`.
5. The full 75-number order is now fixed and stored. Calls just walk this array.

**After the round ends:**
6. Reveal `server_seed`. Any player can recompute the draw and confirm the hash matches.

Expose `GET /api/v1/rounds/{id}/fairness` returning the seed, hash, client seed, and 
resulting draw, plus a short verification snippet. Link it from the results screen.

### 4.2 Ledger — the heart of the money system

Double-entry. Every movement writes **two or more** rows summing to exactly zero.

```sql
CREATE TABLE accounts (
  id        bigserial PRIMARY KEY,
  user_id   bigint REFERENCES users(id),   -- NULL for system accounts
  kind      text NOT NULL,
            -- user_cash | user_bonus | user_locked
            -- house_revenue | house_float | pot_escrow
            -- provider_settlement | promo_expense
  currency  char(3) NOT NULL DEFAULT 'ETB',
  UNIQUE (user_id, kind, currency)
);

CREATE TABLE ledger_transactions (
  id               bigserial PRIMARY KEY,
  kind             text NOT NULL,
                   -- deposit | withdrawal | stake | payout | refund
                   -- commission | bonus_grant | bonus_convert | adjustment
  idempotency_key  text UNIQUE NOT NULL,
  round_id         bigint,
  payment_id       bigint,
  created_by       text NOT NULL,   -- 'system' | 'engine' | 'admin:{id}'
  memo             text,
  created_at       timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE ledger_entries (
  id              bigserial PRIMARY KEY,
  transaction_id  bigint NOT NULL REFERENCES ledger_transactions(id),
  account_id      bigint NOT NULL REFERENCES accounts(id),
  amount          numeric(18,2) NOT NULL,   -- signed; +credit, -debit
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON ledger_entries (account_id, id);

-- Enforced by a DEFERRABLE constraint trigger:
--   SUM(amount) per transaction_id = 0
```

**Balance** is `SUM(amount)` over an account's entries. Do **not** read that live on 
every request — maintain `account_balances (account_id, balance, last_entry_id)` updated 
in the same transaction, and reconcile it against the entry sum nightly. If they ever 
disagree, page someone.

**Available balance for staking** = `user_cash + user_bonus`, minus `user_locked`.

Example — a 20 ETB stake:

| Account | Amount |
|---|---|
| `user_cash` (player 1234) | −20.00 |
| `pot_escrow` (round 88) | +20.00 |

Settlement of that 700 ETB pot:

| Account | Amount |
|---|---|
| `pot_escrow` (round 88) | −700.00 |
| `user_cash` (winner) | +560.00 |
| `house_revenue` | +140.00 |

Money never appears from nowhere. That property is what lets you answer "where did my 
birr go" with a query instead of an apology.

## 5. Redis layout

Redis is for **hot state and fan-out**, never for money. If Redis is wiped, the platform 
must recover fully from PostgreSQL — losing at most the in-flight rounds, which are then 
voided and refunded.

| Key | Type | TTL | Purpose |
|---|---|---|---|
| `room:lock:{room_id}` | string | 15 s | Single-owner election for the engine |
| `room:state:{room_id}` | string (JSON) | 60 s | Latest snapshot, for fast reconnect |
| `room:presence:{room_id}` | set | — | Connected user ids, for the Players counter |
| `ws:user:{user_id}` | string | 300 s | Which gateway holds this user's socket |
| `rl:{scope}:{id}` | string | varies | Token-bucket rate limiting |
| `seen:tg:{update_id}` | string | 600 s | Telegram update dedupe |
| PUB `room:{room_id}` | channel | — | Engine → all gateways |
| PUB `user:{user_id}` | channel | — | Targeted messages (balance changed) |
| STREAM `payouts` | stream | — | Withdrawal job queue with consumer groups |

Use **Redis Streams, not plain lists**, for the payout queue — you need consumer groups 
and acknowledgement so a crashed worker doesn't lose or double-pay a withdrawal.

## 6. Realtime protocol (WebSocket)

`wss://api.jobingo.et/ws?v=1`

### 6.1 Handshake

First frame from client, within 5 seconds or the socket is closed:

```json
{ "t": "auth", "init_data": "<raw Telegram WebApp initData string>" }
```

Server validates the HMAC (§9.1), then replies:

```json
{ "t": "authed", "user": { "id": 1234, "name": "Nebyu", "balance": "340.00" },
  "server_time": 1755849600123 }
```

### 6.2 Client → server

| Type | Payload | Notes |
|---|---|---|
| `rooms` | — | List rooms with live player counts |
| `join` | `{room_id}` | Subscribe to a room's broadcasts; does not stake money |
| `take_card` | `{room_id, card_no, idem}` | Stakes money. Fails if taken/insufficient |
| `drop_card` | `{room_id}` | Only legal during LOBBY; refunds |
| `set_auto` | `{room_id, auto: bool}` | |
| `mark` | `{round_id, r, c}` | Manual marking; server records but does not trust |
| `claim` | `{round_id}` | Assert BINGO |
| `leave` | `{room_id}` | |
| `ping` | `{ts}` | Every 20 s; server replies `pong` |

### 6.3 Server → client

| Type | When | Payload |
|---|---|---|
| `state_sync` | On join and on reconnect | Full room + round + your card + all called numbers |
| `lobby_tick` | Every 1 s in LOBBY | `{seconds_left, players, pot, derash}` |
| `card_taken` | Someone takes/drops a card | `{card_no, taken: bool}` |
| `round_start` | LOBBY → RUNNING | `{round_id, seq, players, pot, derash, seed_hash}` |
| `call` | Every 4 s | `{round_id, index, number, letter}` |
| `claim_result` | After a claim | `{valid, reason?}` |
| `round_end` | Winner or exhaustion | `{winners[], derash, pattern, cells, server_seed}` |
| `balance` | Any ledger change | `{cash, bonus, locked}` |
| `error` | Any rejected command | `{code, message_en, message_am}` |
| `pong` | Reply to ping | `{ts, server_time}` |

### 6.4 Fan-out efficiency rules

- **Never** send the whole board on every call. Send only the new number; the client 
  accumulates. Send the full set only in `state_sync`.
- Pre-serialize the `call` message **once per room**, then write the same bytes to every 
  socket. Do not `json.dumps` per connection.
- Batch `lobby_tick` for all rooms on a shared 1 Hz timer, not per-room timers.
- Coalesce: if a socket's send buffer is backed up more than 64 KB, drop the tick 
  messages for that socket and queue a `state_sync` instead. A slow client must never 
  slow the room.
- Compress with `permessage-deflate` only above 512 bytes; below that it costs more 
  CPU than it saves.

### 6.5 Reconnection

Client stores nothing authoritative. On reconnect it sends `auth` then `join`, and the 
server replies with `state_sync` containing `call_index`, the full `called` array, and 
a `server_time` so the client can align its countdown animation. Total recovery: one 
round trip.

## 8. Payment system

### 8.1 Provider strategy

Ethiopian rails, in priority order:

| Provider | Covers | Use for |
|---|---|---|
| **Chapa** | Telebirr, CBE Birr, M-Pesa, banks, cards | Primary deposits + payouts |
| **SantimPay** | Telebirr, banks | Failover deposits |
| **ArifPay** | Telebirr, cards | Second failover |
| **Manual** | Direct bank transfer + receipt upload | Long tail, large amounts |

Build a **provider-agnostic interface** so adding a rail is a new adapter, not a rewrite:

```
PaymentProvider
  ├─ create_checkout(amount, user_ref, our_ref, return_url) -> {checkout_url, provider_ref}
  ├─ verify_webhook(headers, raw_body)                      -> VerifiedEvent | InvalidSignature
  ├─ fetch_status(provider_ref)                             -> PaymentStatus
  └─ create_payout(method, amount, our_ref)                 -> {provider_ref, status}
```

**Never trust a redirect back to your `return_url` as proof of payment.** The webhook is 
truth, and if the webhook is late, `fetch_status` polling is the fallback. A user 
returning to the app sees "confirming your deposit" until one of those two confirms.

### 8.2 Deposit flow

```
1. User picks amount           → validate: >= MIN_DEPOSIT, <= daily cap, user not banned
2. Create payments row         → status 'pending', our_ref 'DEP-{yyyy}-{seq}'
3. provider.create_checkout()  → status 'processing', store provider_ref
4. Bot sends the checkout URL as an inline button
5. User pays on Telebirr/bank
6. Provider POSTs webhook      → verify signature FIRST, reject 401 if bad
                               → dedupe on (provider, event_id)
                               → if already 'succeeded', return 200 and stop (idempotent)
7. In ONE db transaction:
     - payments.status = 'succeeded'
     - ledger txn 'deposit': provider_settlement -amount, user_cash +amount
     - update account_balances
8. Publish to Redis user:{id}  → live balance update in the Mini App
9. Bot notification: "✅ 200 ETB deposited. Balance: 340 ETB"
```

**Reconciliation job**, hourly: pull the provider's settlement report, match on 
`our_ref`, and flag any payment where provider and ledger disagree. This catches the 
webhook you never received before the customer does.

### 8.3 Withdrawal flow

Withdrawals are where fraud lives. Deliberately slower than deposits.

```
1. User requests amount + payout method
2. Validation gate:
     - amount >= MIN_WITHDRAW
     - available cash balance covers it (bonus funds are NOT withdrawable)
     - wagering requirement on any active bonus is met
     - kyc_level >= 2 if amount > KYC_THRESHOLD (e.g. 5,000 ETB)
     - payout method holder_name matches account name
     - no deposit in the last 30 min via a reversible rail (chargeback window)
3. Immediately move funds: user_cash -amount → user_locked +amount
     This is the single most important step. The money is gone from their
     playable balance the moment they ask. No double-spend, ever.
4. Auto-approve if ALL of:
     - amount <= AUTO_APPROVE_LIMIT (e.g. 2,000 ETB)
     - account age > 24 h
     - risk score below threshold
     - lifetime deposits >= lifetime withdrawals
   Otherwise → status 'review', lands in the admin queue
5. Approved → push job onto Redis Stream 'payouts'
6. Payout worker calls provider.create_payout(), with a
   consumer-group ack so a crash cannot double-send
7. On provider success, ONE db transaction:
     user_locked -amount, provider_settlement +amount
     payments.status = 'succeeded'
8. On failure/rejection: user_locked -amount, user_cash +amount (reversal)
   Bot notifies the user with the reason.
```

### 8.4 Anti-fraud rules to encode

| Rule | Action |
|---|---|
| Deposit → withdraw with almost no play ("balance laundering") | Hold for review |
| Same payout account across multiple accounts | Link accounts, flag cluster |
| Multiple accounts, same device fingerprint, in the same room | Collusion flag |
| Winner and loser in the same room repeatedly, same pairs | Collusion investigation |
| Withdrawal velocity > 3/day | Review |
| Referral chain where referee never deposits | No reward |

### 8.5 Bonuses and wagering

Bonus balance is a **separate account kind**, spendable but not withdrawable. Attach a 
wagering requirement (e.g. bonus must be staked 5×) and track progress in the `bonuses` 
table. When requirement is met, run a `bonus_convert` ledger transaction moving the 
remainder from `user_bonus` to `user_cash`. Never let bonus and cash blur together — 
that ambiguity is how support tickets become disputes.

## 9. Security

### 9.1 Telegram Mini App auth

The only identity source. Validate on **every** WebSocket handshake and every REST call:

```
1. Parse initData query string into key/value pairs
2. Extract and remove the 'hash' field
3. data_check_string = keys sorted alphabetically, joined "k=v" with \n
4. secret_key = HMAC-SHA256(key="WebAppData", message=BOT_TOKEN)
5. computed = HMAC-SHA256(key=secret_key, message=data_check_string)
6. Compare to hash with constant-time comparison
7. REJECT if auth_date is older than 24 hours (replay protection)
```

Constant-time compare, not `==`. And **reject stale `auth_date`** — this is the step 
most implementations skip, and it turns a captured initData string into a permanent 
session token.

### 9.2 Other controls

- **Transport:** TLS 1.2+ everywhere, HSTS, secure WS only.
- **Rate limits:** per-user token buckets — `claim` 5/round, `take_card` 10/min, 
  `deposit` 5/hour, WS messages 30/s. Per-IP limits at the edge for the rest.
- **Bot token** and provider keys in a secret manager, never in the repo or image.
- **Webhook signature verification** mandatory; log and alert on failures.
- **SQL:** parameterized only. **No** string-built queries anywhere near money.
- **Admin panel:** separate auth (not Telegram), TOTP required, IP allowlist, every 
  action written to the immutable `audit_log`.
- **PII:** phone numbers encrypted at rest; logs must never contain full numbers or 
  `initData` strings.
- **Backups:** PostgreSQL PITR with WAL archiving, 30-day retention, and a **restore 
  drill run monthly** — an untested backup is not a backup.

## 10. Scale and deployment

### 10.1 Runtime

| Component | Choice | Rationale |
|---|---|---|
| Language | Python 3.12 (asyncio) | Fast to build, plenty of Ethiopian devs. Go for the engine if you later need it |
| Web framework | FastAPI + uvicorn/uvloop | Native async WS |
| Bot | aiogram 3 (webhook) | Mature, async |
| DB | PostgreSQL 15 + PgBouncer | Transactional integrity is the whole game |
| Cache/bus | Redis 7 (cluster mode) | Pub/sub + streams + locks |
| Deploy | Docker + Kubernetes (or Docker Swarm to start) | Independent scaling per service |
| Edge | Cloudflare or nginx | TLS, WS upgrade, DDoS, rate limits |

Kubernetes is the right answer at 10k concurrent, but do not start there. Ship v1 on 
three VPS boxes with Docker Compose, prove the game is fun, then migrate. Premature 
orchestration has killed more Ethiopian startups than load has.

### 10.2 Scaling knobs, in the order you will need them

1. **Add Gateway replicas.** Stateless, linear, handles the connection count.
2. **Add Engine shards.** Rooms redistribute via the Redis lock automatically.
3. **Read replicas** for history/leaderboard queries.
4. **Partition** `ledger_entries` and `rounds` by month once past ~50M rows.
5. **Move the engine to Go** only if Python's GIL actually becomes the bottleneck — 
   measure first; at 100 calls/sec it will not.

### 10.3 Load test targets (must pass before launch)

| Scenario | Target |
|---|---|
| 10,000 concurrent WS, 200 rooms, 30 min soak | No dropped sockets, memory flat |
| 1,000 players joining one stake tier in 10 s | All seated or cleanly rejected, no double-charge |
| Kill an Engine pod mid-round | Round voided + fully refunded, or resumed; never silently lost |
| Kill a Gateway pod with 8,000 sockets | Clients reconnect within 5 s with correct state |
| Redis failover | Rounds void safely; balances unaffected |
| Duplicate webhook × 100 | Exactly one deposit credited |

Use k6 or Locust with a WebSocket scenario. **Do not launch on untested assumptions 
about concurrency** — a bingo app that stutters during the number call is a dead app.

### 10.4 Observability

- **Metrics** (Prometheus + Grafana): concurrent connections, rooms active, calls/sec, 
  call-to-ack p50/p95/p99, claim validation time, ledger txn/sec, deposit success rate, 
  payout queue depth, house revenue live.
- **Logs** (structured JSON → Loki): every ledger transaction, every claim, every admin 
  action, every webhook.
- **Traces** (OpenTelemetry): deposit and payout paths end to end.
- **Alerts:** balance reconciliation mismatch (page immediately), payout queue depth > 50, 
  deposit success rate < 90%, p99 call latency > 1 s, any round voided.

## 12. Compliance and responsible gaming

Real-money gambling is regulated. In Ethiopia this falls under the **National Lottery 
Administration**, and rules for online betting have changed repeatedly in recent years — 
including periods of suspension for online sports betting. Before taking a single birr:

- Confirm current licensing requirements with the NLA and a local lawyer.
- Confirm what your payment provider's terms allow — Chapa and others have gambling 
  clauses, and getting shut off mid-operation is a business-ending event.
- Understand tax obligations on gross gaming revenue and on player winnings.

Build these in from day one, not after a regulator asks:

- **Age gate:** 18+ declaration at registration, ID verification at KYC level 2.
- **Deposit limits:** daily/weekly caps, user-settable downward instantly, upward only 
  after a 24-hour delay.
- **Loss limits** and **session-time reminders** ("you've been playing 60 minutes").
- **Cool-off:** 24 h / 7 d / 30 d, self-service.
- **Self-exclusion:** 6 months minimum, irreversible for the period, blocks 
  registration by the same phone.
- **Reality check** on the results screen: net position this session, shown plainly.
- **Support links** to problem-gambling help in Amharic.
- **Never** send win-back promotions to self-excluded or cooled-off users. Segment your 
  notification queries by `users.status` at the query level so it can't be forgotten.

## 14. Definition of done

The platform is ready when:

- [ ] Ledger sum equals balance cache for every account, verified nightly, zero drift over 30 days
- [ ] Every win pattern has a unit test, including edge cases with the free space
- [ ] A killed engine pod mid-round results in a full refund or clean resume — proven by chaos test
- [ ] 100 duplicate webhooks credit exactly one deposit — proven by test
- [ ] 10,000 concurrent sockets sustained 30 minutes with p99 call latency < 300 ms
- [ ] A player can independently verify any round's draw from the published seed
- [ ] Self-exclusion blocks play, deposits, and marketing — proven by test
- [ ] A full restore from backup has been performed in the last 30 days
- [ ] Amharic is complete across bot, Mini App, and error messages
