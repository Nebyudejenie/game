# Bot Command Catalog

Generated by directly introspecting `services/bot/handlers.py`'s real
aiogram `Router` (`python -c "from services.bot.handlers import router; ..."`,
not hand-maintained), so this list cannot silently drift from what the bot
actually runs. Re-run the introspection above after any handler change to
verify this table before trusting it again. Independently re-verified at
the start of the Telegram Command Center phase (Phase 2) -- still exactly
18 handlers, 13 slash commands, 5 other matchers, 0 callback/inline
handlers, matching the count from the prior Telegram command latency
diagnosis phase.

Every one of the 18 handlers now also has a row in the `bot_commands`
table (`migrations/versions/232a259a3baa_bot_command_registry.py`), the
single source of truth described in `docs/TELEGRAM_COMMAND_OPERATIONS.md`
-- one row per real `handler_name`, seeded on the same migration that
creates the table, so the registry was never empty/unmanaged on day one.

**There are no callback query, inline query, or button-press handlers
anywhere in this codebase today** — every interactive surface is either a
slash command, a plain-text message match, a shared contact, or a photo
upload. `web/miniapp`'s own buttons talk to the gateway's WebSocket API
directly, never through the bot. Sections of the parent directive asking
about "callback/button performance" (inline keyboards) describe a
feature that does not exist in this codebase; nothing was built or
measured for it because there is nothing to measure.

## Registered handlers (message observer), in registration order

Registration order matters: aiogram stops at the first handler whose
filters all pass, so a specific command handler registered before a
catch-all (e.g. `on_agent_portal_command`'s `Command("portal")` before
`on_agent_sms`'s bare `F.text`) is what keeps `/portal` from being
swallowed as a forwarded SMS — `tests/integration/test_bot_handlers.py::
test_portal_command_sends_a_login_link_only_to_an_active_agent` is the
regression test for exactly that.

## What "admin-configurable" actually means today

**The registry now exists** (`bot_commands`, seeded with all 18 rows on
the same migration that creates it -- see `docs/
TELEGRAM_COMMAND_OPERATIONS.md` for the full design). 15 of 18 handlers
are fully admin-manageable: enable/disable, description, category, sort
order, cooldown, rate limit value, content key, and analytics key, all
through `GET/PATCH /telegram/commands` and the Admin Dashboard's
Telegram screen, every change audited. 3 handlers (`cmd_start`,
`on_contact`, `on_menu_text`, `on_unhandled_message` -- the registration
entry point and the core dispatch plumbing) are `admin_managed=false`:
their description/content is still editable, but they cannot be disabled
from the admin UI, because doing so would lock out new players or break
every reply-keyboard button at once with no recovery path except a code
deploy. This is a deliberate, narrow exception, enforced server-side
(`command_registry_queries.CommandNotAdminManaged`), not just a hidden
button.

**Phase 3 update**: `cooldown_seconds` and `rate_limit_per_minute` are
now genuinely enforced by `services/bot/command_registry.py::
command_gate_middleware`, not just stored -- see
`docs/TELEGRAM_COMMAND_OPERATIONS.md` §6 for the full design. Every
command in the table above shows "Enforced (Phase 3) when configured" in
its Rate limit column: none has a non-default cooldown/rate-limit value
set out of the box (every seeded row ships with `cooldown_seconds=0`,
`rate_limit_per_minute=NULL`), so this is zero behavior change until an
admin actually opts a specific command into a limit through the Commands
screen. `analytics_key` is also now genuinely wired into every metric
this codebase attributes to a command (same doc, §7) -- no command has
one set by default either, so this too is a no-op for the existing
Grafana dashboard until an admin sets one.

## What "Content source" means

Every reply already goes through `services/bot/i18n.py::t()`, with a
real, tested am → en → am fallback chain
(`tests/unit/test_bot_no_hardcoded_strings.py` enforces "no hardcoded
user-facing string anywhere in `handlers.py`"). Bot Content admin
overrides (`services/bot/bot_content_sync.py`, from an earlier pass)
already let an admin edit specific keys without a deploy — this
catalog's "Content source" column doesn't distinguish "file default" from
"admin override" per row because `t()` resolves that transparently and
identically for every command; see `docs/CONTENT_STUDIO.md`-equivalent
prior work if/when a unified Content Studio ships.
